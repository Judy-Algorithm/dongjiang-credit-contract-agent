# 东江一体化信审与合同评审 Agent 架构

## 1. 设计原则

1. 规则负责底线，模型负责增强：授信、账期和法律底线由版本化规则确定，LLM 不得覆盖硬规则。
2. 数据先脱敏再出边界：原始文件在本地解析，可逆映射保存在案件隔离区；外部模型只接收脱敏副本。
3. 每个结论都有证据：评分维度、合同事实、命中规则、原文片段、修改建议和审批路由均进入案件 Trace。
4. 端口与供应商解耦：业务层只依赖 `CRMPort` 和 `OAPort`，后续替换为东江 CRM、泛微 OA API。
5. 人机协同：Agent 输出通过、复核、特批或阻断建议，最终信用决策和合同修改由授权人员确认。
6. 动态分析、静态合规：运行时可以按案件资料选择并行分析任务，但政策阈值、审批权限、人工门禁和系统回写条件不能由模型动态改写。

## 2. 受控动态工作流

当前采用“静态合规主干 + 动态分析计划 + 独立核验”的混合架构。`workflow/dynamic.py`
根据客户类型、业务类型、资料覆盖、合同份数和文本模型可用性生成结构化计划；所有任务必须来自
`TASK_CATALOG`白名单，并通过任务数、依赖引用和无环校验。计划是数据，不是模型生成后直接执行的
Python或JavaScript代码。

计划规范版本为`2.0`。每份计划在执行前冻结，并对案件号、任务目录版本、任务依赖、输入引用和
运行时版本快照计算SHA-256。父图和子图扇出前都会重新校验规范哈希；任何运行中篡改都会被拒绝。
运行时快照只保存信用规则、合同规则、模型和提示词的版本及摘要，不保存API密钥。相同案件输入、
任务规范和版本快照产生相同计划ID及节点幂等键，规则或提示词变化则自动形成新计划身份。

信用子图按案件动态展开资料完整性、财务、评级、历史交易、企业基础、信用控制和TKM专项任务，
汇总后再调用确定性信用评分器，并由独立核验节点检查政策版本、评分范围、风险等级和补件一致性。
合同子图按合同份数并行展开制度规则审查和可选AI辅助审查，逐份汇总后由独立核验节点检查制度
结论、授信交叉校验、AI辅助边界和证据覆盖。

节点先查LangGraph Checkpoint，再查`data/executions/<case>/<plan>/<key>.json`持久执行缓存；命中后
复用结果而不重复调用规则引擎或模型。合同AI任务最多尝试两次，连续失败时回退到制度规则；AI发现
的证据定位率低于80%时剔除未定位发现并标记降级。独立核验节点比较计划和实际结果，检查缺失、
越权、重复、证据违规与规范完整性。审计不一致时，信用流程强制补件，合同流程至少进入人工复核，
且不会把原有阻断或特批结论降级。

案件保存计划版本、任务状态、耗时以及脱敏输入/输出摘要。前端“Agent运行”页签展示父工作流、
两个子Agent、冻结短哈希、版本快照、尝试次数、幂等复用和偏差审计；合同原文、客户敏感字段、
Vault映射、完整哈希和密钥不会写入运行日志或业务页面。

Cloudflare Dynamic Workflows尚未成为运行依赖。后续可用于公网事件接收、等待OA回调和持久重试，
但只传案件号、任务类型、脱敏摘要和文件引用，本地Python服务继续负责文档解析、脱敏、评分与审查。

## 3. 业务链路

```text
本地资料/CRM
  → 多格式解析与文件分类
  → 本地敏感信息识别、脱敏与隔离映射
  → 查询180天内有效信审结果
      ├─ 有：读取批准额度、账期和特殊条件
      └─ 无：财务 + 外评 + 合作记录 + 企业基础 → 东江评分模型
  → TKP/TKM政策计算额度、账期和尾款条件
  → 当前未收款 + 在手订单占额 → 可用额度计算 → 逾期30天锁定/特别放行
  → 信用审批人审批 → 授信生效
  → 合同门禁开放 → 业务经办人上传合同 → 合同事实提取
  → 完整性 + 信用交叉校验 + 法律风险规则
  → 合并去重、定位原文、给出修改建议
  → 正常审批 / 合同法务复核 / 授权审批人特批 / 原则阻断
  → 报告导出及 OA/CRM 回写
```

## 4. 代码边界

```text
dongjiang_agent/
├── workflow/       Harness、动态计划白名单、LangGraph父图/子图、Interrupt与Checkpoint
├── ingestion/      DOCX表格/PDF逐页OCR/XLSX/图片/文本提取与证据坐标
├── security/       可逆本地脱敏和隔离 Vault
├── credit/         信用事实提取与可解释评分子 Agent
├── contract/       合同事实提取、规则审查、Word修订与多语言版本
├── config/         版本化信用政策与合同规则
├── persistence/    案件、有效信审与节点幂等执行缓存
├── operations/     节点SLA、逾期提醒、历史分析及管理报表导出
├── integrations/   CRM/OA 端口及 Webhook 适配器
├── llm/            只接受脱敏文本的可选模型增强
├── reporting/      JSON/HTML 审评报告
└── web/            本地业务API与多页面前端
```

CLI、Web、CRM和OA统一通过`workflow/DongjiangWorkflowHarness`启动和恢复，
不再维护第二套同步编排。Harness把`case_id`作为LangGraph `thread_id`，并用
SQLite保存本地Checkpoint。

## 5. 决策状态机

优先级从高到低：

1. 命中不可直接接受的合同底线：`block → return_to_owner`
2. 超批准额度、超建议/常规信用条件或需高层授权的重大法律风险：`special_approval → director_ceo`
3. 关键字段或条款缺失：`manual_review → finance_legal`
4. 未命中风险：`pass → normal`

当前常规信用条件：

- TKP 一般不超过 Net 90 天，终端项目统一账期或授权审批人（如市场总监）特别批准可例外。
- TKM 一般尾款比例不超过 40%、尾款账期不超过 180 天，超出时由授权审批人处理特别信用申请。

无责取消、关联主体责任外溢、间接损失等合同底线命中后退回修改；连带责任、排他、银行承兑等按底线表进入相应授权审批。上述制度口径来自比赛材料；模型权重、覆盖率和等级阈值属于比赛建议值，不得标注为东江正式制度。

信用控制层另行执行：未收款和在手已入单金额合计不得超过批准额度；当前未收款逾期超过30天时锁定合同入口。特别放行与合同特批均须归档附件，并记录文件SHA-256、审批人和时间。
